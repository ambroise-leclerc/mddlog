# Migration de v0.2 vers l’API retenue pour 1.0 (#121)

Ce guide rassemble ce qu’un intégrateur de v0.2.0 change pour adopter l’API et le paquet
**candidats** à la 1.0. La politique de compatibilité est celle d’[ADR-007](../adr/ADR-007-compatibility-and-distribution.md),
proposée pour revue ; le gel final attend les retours de #122. Rien ici ne qualifie un dispositif.

## Ce qui ne change pas

- Tous les noms exportés par `import mddlog;` en v0.1.0, v0.2.0 et v0.3.0 restent exportés :
  [l’inventaire](../api/public-surface.json) est comparé aux tags publiés par
  `scripts/check-compatibility.py --git`, qui refuse une suppression non enregistrée.
- Les octets canoniques, le layout des segments, les ancres, le protocole du témoin, la position
  retenue et les formats d’export gardent leur version 1. Les archives réelles
  [v0.2.0 et v0.3.0](../../tests/archives/audit-export/README.md) restent lues et vérifiées.
- Les méthodes historiques (`logMedical`, `logAudit(AuditInput)`, la façade `Log`) restent
  disponibles. Les exemples « avant » ci-dessous compilent toujours.

## Paquet CMake et consommateur

Changements **incompatibles pour un projet consommateur** livrés par ce lot :

| v0.2 / v0.3 | Retenu | Action |
| --- | --- | --- |
| `find_package(mddlog 0.2)` acceptait toute version plus récente | `SameMinorVersion` avant 1.0, `SameMajorVersion` ensuite | Demander la version visée, par exemple `find_package(mddlog 0.3 CONFIG REQUIRED)` |
| `mddlogConfig.cmake` modifiait le répertoire du consommateur (`CMAKE_CXX_STANDARD`, `add_compile_options`, `CMAKE_CXX_MODULE_STD`) | Aucune variable ni option globale n’est modifiée | Le consommateur fixe C++23, la porte `import std` avant `project()` et `CMAKE_CXX_MODULE_STD` |
| Macros `MDDLOG_VERSION_*`, `MDDLOG_PLATFORM_*`, `NOMINMAX`, `WIN32_LEAN_AND_MEAN` et options `/W4`, `/permissive-`, `-fconcepts-diagnostics-depth` propagées | Paramètres privés de mddlog | Interroger `mddlog::getVersion()` ; définir soi-même ses macros Windows |
| Avertissements `-Werror` de mddlog appliqués à la reconstruction des BMIs installés | `mddlog_warnings` n’est plus installé ni exporté | Aucune |
| Modules installés sous `include/modules/include/mddlog/` | `include/modules/mddlog/` | Aucune pour `find_package` ; adapter un chemin écrit en dur |
| Pas de composant | `COMPONENTS core full file_storage audit_tool`, cible `mddlog::audit_tool` | Demander les composants optionnels utilisés |
| Compilateur non contrôlé | Refus explicite si le compilateur ou sa version diffère de la construction | Reconstruire mddlog avec la chaîne du consommateur |

Les exigences complètes du consommateur et les constats de ses options sont décrits dans
[le document dédié](../consumer-requirements.md) ; la matrice qualifiée dans
[la matrice de compatibilité](../compatibility-matrix.md).

## Diagnostic contextuel

Avant, les identifiants sont répétés positionnellement :

<!-- snippet: tests/consumer/package/MigrationExamples.cpp#diagnostic-before -->
```cpp
// v0.2: identifiers repeated positionally at every call.
void primeBefore(mddlog::SimpleLogger& logger) {
    logger.logMedical(mddlog::LogLevel::Info, "Priming", "pump", "nurse-7", "session-2", "pump-1");
    logger.logMedical(mddlog::LogLevel::Info, "Primed", "pump", "nurse-7", "session-2", "pump-1");
}
```

Après, l’hôte prépare un `DiagnosticContext` au point de composition et injecte une liaison :

<!-- snippet: tests/consumer/package/MigrationExamples.cpp#diagnostic-after -->
```cpp
// Retained: the host prepares the context once; business code passes only the message.
void primeAfter(mddlog::DiagnosticBinding<mddlog::SimpleLogger>& logger) {
    logger.info("Priming");
    logger.info("Primed");
}
```

Détails : [contextes et liaisons](contextual-logging.md).

## Budgets du diagnostic

La file asynchrone de `SimpleLogger` est bornée depuis #118. Les signatures historiques
compilent ; sous saturation, le message le plus récent est refusé et compté. Choisissez les
budgets et observez l’admission au point de composition :

<!-- snippet: tests/consumer/package/MigrationExamples.cpp#bounded-composition -->
```cpp
// Retained: budgets are chosen at the composition point; admission is observable.
[[nodiscard]] bool composeDiagnostics() {
    mddlog::SimpleLogger logger("pump", mddlog::DiagnosticConfig{.messageCapacity = 64, .maxRecordBytes = 256}, false);
    if (logger.tryLog(mddlog::LogLevel::Info, "Ready") != mddlog::DiagnosticStatus::Success)
        return false;
    return logger.flushChecked().status == mddlog::DiagnosticStatus::Success && logger.health().admitted == 1;
}
```

Détails : [budgets du diagnostic](bounded-diagnostics.md).

## Audit avec description et contexte

Avant, chaque `AuditInput` répète les invariants :

<!-- snippet: tests/consumer/package/MigrationExamples.cpp#audit-before -->
```cpp
// v0.2: every invariant field is restated in each AuditInput.
[[nodiscard]] bool doseBefore(mddlog::SimpleLogger& logger) {
    return logger
        .logAudit({.category       = mddlog::AuditCategory::Configuration,
                   .phase          = mddlog::AuditPhase::Requested,
                   .action         = "pump.rate.change",
                   .actor          = "nurse-7",
                   .target         = "pump-1",
                   .requirementRef = "REQ-12",
                   .correlationId  = "call-9"})
        .wasAdmitted();
}
```

Après, description et contexte sont validés une fois ; phase et temps restent explicites :

<!-- snippet: tests/consumer/package/MigrationExamples.cpp#audit-after -->
```cpp
// Retained: description and context are validated once; phase and time stay explicit.
template <std::size_t Capacity>
[[nodiscard]] bool doseAfter(mddlog::AuditRing<Capacity>& ring) {
    const auto description = mddlog::AuditDescription::create(
        {.category = mddlog::AuditCategory::Configuration, .action = "pump.rate.change", .requirementRef = "REQ-12"});
    const auto context = mddlog::AuditContext::create({.actor = "nurse-7", .target = "pump-1", .correlationId = "call-9"});
    if (!description || !context)
        return false;  // A refused identifier is handled before any emission.
    mddlog::AuditBinding audit(ring, *description, *context);
    return audit.record(mddlog::AuditPhase::Requested, mddlog::RawTime::unavailable()).wasAdmitted();
}
```

Détails : [admission d’audit](audit-admission.md) et [contextes](contextual-logging.md).

```cpp
// Retained: query the version through the module; the MDDLOG_VERSION_* macros are no longer
// defined in consumer translation units.
[[nodiscard]] bool versionKnown() {
    return !mddlog::getVersion().empty();
}
```

## Vérification

Ces extraits sont des régions de [MigrationExamples.cpp](../../tests/consumer/package/MigrationExamples.cpp),
compilées et exécutées dans l’arbre (`SourceTreeMigrationExamples`) et par chaque
consommateur indépendant (`InstallTreeConsumer`, `SourceSubdirectoryConsumer`,
`SourceArchiveConsumer`). `scripts/check-compatibility.py` refuse un extrait différent de
sa région. Les autres guides de [docs/migration](.) restent la référence de chaque sujet.
